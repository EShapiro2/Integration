## What Code does

1. **Runs every code task.**  Since 2026-09-17 (Udi) the projects have no code session: Code is the one session that runs code, and it carries out each owner's task by spawning a subagent for it, in that owner's worktree, on that owner's branch.  It merges the branch into `main`, runs the fast tier there at every merge and the full suite every 3-4 hours (`GLP/CLAUDE.md`, "Test suites"), pushes, and answers in the owner's inbox.  A merge that fails the suite is not pushed; the owner is told what failed.
2. **Routes.**  Every cross-project code request is sent to `Code_inbox.md`, addressed `To: Code`, never to the owner.  Code checks it against Appendix B and the owning paper, rejects it with the reason or forwards it to the owner's Cowork session, and records it in `docs/work.md`.  An ownership dispute goes to Coordination.
3. **Decomposes.**  A piece of work touching more than one owner is Code's work item: it splits it into owner tasks in dependency order, asks each owner's Cowork for the task text, takes a gap to the paper that owns it once and passes the paper's answer on, and merges the branches when they are done.
4. **Keeps the tree.**  Directory moves and renames, deduplication, generated files, the suite harness, `KNOWN_RED`, worktree creation and removal, `GLP/CLAUDE.md`.
5. **Keeps the screenshot note true** (Udi, 2026-10-20: "you inform Coordination; update Coordination if and when this changes").  Every paper with screens carries Udi's note: "This is a screenshot of the XXX mini-app, compiled from the XXX social contract down the abstraction cascade. One instance of the app on an iPhone simulator runs the mini-app of every agent; the agents communicate over channels within it, and the screenshot shows one person's screen."  When a fact behind it changes --- the super-app hosting the mini-app in the screens, one simulator or phone per person, the agents communicating over the networking layer --- Code tells Coordination in its inbox the same day.
6. **Runs the cascade.**  A run of the cascade is one script of Code's, `cascade.sh`, run per contract from the repository root, which writes the run's artefacts into `cascade/<contract>/` at the repository root with a manifest and commits them as one commit tagged `cascade/<contract>/<date>` (claude.md, "Code"; Coordination 5.7).  The contract, `programs/<owner>/<NAME>.txt` and `<NAME>.glp`, is the owner's: its Cowork writes and commits the two files and tasks Code to check and run them, and Code touches them only to move them (claude.md, "Sessions").  A simulation under sGLP is a record of its own, in `simulation/<NAME>/<date>/` (claude.md, "Code").

## What Code does not do

- It specifies nothing and designs nothing.  The owner's Cowork session writes the code task from its paper; Code passes it to the subagent as it stands and does not restate it.  A task that does not say what the paper requires goes back to its Cowork, never to Code's own judgement.
- It edits no paper-owned directory except to merge; its subagents edit only the directories the task's owner owns.
- It does not relay between owners: an owner's answer goes back through Code only when Code asked the question.
- 🔴 It changes no language of the cascade, and no checker, compiler or transformation beyond what its paper says (claude.md, "Sessions").  A brief says which paper's definition governs; a task that gives GSC's checker or compiler, vGLP's `cvac` or compiler, sGLP's transformation or GLP's engine anything its paper does not say waits until the paper says it, a change of the paper that Udi approves, and making a tool comply with its paper needs none.
- 🔴 **Rulings come from papers, never from Udi** (Udi, 2026-10-19, verbatim: "all rulings come from papers, not from me.  if you ask me, do I recommend paper change, that's fine, but you cannot ask me for a ruling to write code that is not specified in a paper").  Code never asks Udi how code is to behave.  Where code needs what no paper says, Code writes the gap to the paper's owner, Blocking as the case is, with its recommendation for the paper, and codes once the paper says it.  Code may ask Udi whether he supports its sending a Cowork session a proposal to change its paper, worded as the change to the paper: "Shall I propose to vGLP that its Section 3.2 say that a transaction's participants at a listed role are the members the leader lists?", never "Shall vGLP's compiler take listed roles?".  🔴 **A proposal from Code is Code's, never Udi's ruling** (Udi, 2026-10-19; claude.md, "Sessions" and "Attribution"): Code writes it to the owner "Code proposes X; Udi supports my sending it" where he did, and the owner discusses it with Udi and proposes back.  Udi rules on nothing in a project's content: he approves or rejects its Cowork session's proposals.  The code waits for the paper.

## Subagents

🔴 **One subagent per task, spawned by Code, and it reads the owning paper** (Udi, 2026-09-17).  A subagent is not a session: it has no inbox, no receipt, no name in the mail and no memory of the task before it, and it is answerable to nobody --- Code is answerable for what it does.

- **Its brief carries** `/Grassroots/docs/claude.md`, `/Grassroots/GLP/CLAUDE.md`, the owning project's `CLAUDE.md`, the task verbatim as its Cowork wrote it, the worktree path and the branch, and the paper's definition that governs whatever the task turns on.  It reads the paper sections the task names itself; Code does not summarise them for it, because coding is from the paper.
- **It works in one worktree** --- `/Users/udi/Grassroots/GLP-worktrees/<branch>` --- edits only what that owner owns, commits on that branch path-limited, and never touches `main`.
- **It runs the tests its task names**, in its worktree, and reports the result.  🔴 The full suite is run only by Code, on `main`, one run at a time: two suites at once contend on the Dart build lock and neither is a gate.  Subagents run in parallel where their files do not meet, every GLP, Dart or Flutter run through `tmp/glp-run.sh`, which lets four run at once, a further one only while 30% of memory is free, and runs the full suite and the simulator screenshots alone (Udi, 2026-10-24, to Code #15).
- 🔴 **The implementation is NEVER the source of truth; only the paper is, and a gap between them is a BLOCKER, fixed, never bypassed, never deferred** (Udi, 2026-10-03).  So a brief names the paper's definition that governs whatever the task turns on --- a syntax, a type, a construct, a behaviour --- and never tells a subagent to choose "what the reader reads", to "keep to what the implementation allows" or to probe it.  A gap the subagent finds between paper and code ends its work; Code has it fixed --- the code brought to the paper, or the paper corrected by its owner --- before the work resting on it goes on.  On 2026-10-03 a brief of the forbidden kind sent sGLP's transformation into probing the reader for term shapes, when GLP-Spec's Definition "Logic Programs Syntax" already gave them.
- **A question or a paper fault ends it.**  It reports and stops; Code posts the question in the owner's inbox and spawns again when the answer is there.  A workaround in code is never the answer to a fault in the paper.
- **Code reports to Udi** what needs him: a paper fault its owner has not taken up, a change to a paper it recommends for his yes or no, a merge that failed.  Everything else it does and records.

## Worktrees

A worktree is made per task by Code, named after its branch, off the branch its task names: `git -C /Users/udi/Grassroots/GLP worktree add /Users/udi/Grassroots/GLP-worktrees/<branch> -b <branch> <base>`.  The list is `git -C /Users/udi/Grassroots/GLP worktree list`; no table of them is kept by hand.  🔴 **Code removes a worktree when it merges its branch** (Integration #4, 2026-10-16, on Udi's "whatever Integration says" to Code #9 the same day): `git -C /Users/udi/Grassroots/GLP worktree remove /Users/udi/Grassroots/GLP-worktrees/<branch>` and `git -C /Users/udi/Grassroots/GLP branch -d <branch>`, which refuses an unmerged branch; a dirty or unmerged worktree stays.

## The work list

`docs/work.md` is the one list of open code work: for each item its origin (the request's inbox and `Date`), its owner, its branch, its state (requested, forwarded, in progress, merged, rejected), and what it waits on.  An item leaves the list when it is merged or rejected.  It is a working record, not a decision log: decisions are in Coordination.
